# LLM runtime for v1

Live Hard Constraint / Preference / Relevance judging and Prepare (Gap Report / Tailored CV / Edit Summary) use one **OpenAI-compatible** HTTP client. Credentials and model come from the environment only: `JOB_FINDING_ASSISTANT_LLM_API_KEY` (required for live calls), optional `JOB_FINDING_ASSISTANT_LLM_BASE_URL` (default OpenAI), and `JOB_FINDING_ASSISTANT_LLM_MODEL` (one model for both `LlmJudge` and `LlmCvTailor`; default when unset e.g. `gpt-4.1-mini`). No key or model UI, no disk-stored secrets, no multi-provider SDK surface in v1.

OpenAI-compatible hosts (e.g. DeepSeek) need their own model id — do not leave the OpenAI default when pointing elsewhere. Example: `JOB_FINDING_ASSISTANT_LLM_BASE_URL=https://api.deepseek.com` and `JOB_FINDING_ASSISTANT_LLM_MODEL=deepseek-chat` (or the host’s current chat model). Assessment Summary load (`Assistant.load_assessment_summary_catalog` on `GET /`) may process **at most five** Pending Job Postings per load (sequential in that request; refresh to continue). Each attempt (saved, skipped, or non-unavailable failure) consumes one unit of that budget. On **LLM Unavailable** for an attempt, stop the rest of that load’s budget early. A judge failure or skip must **not** starve later Pending ids: the process defers the failed head and advances the queue, then retries deferred heads after a full pass. HTTP calls use a short timeout and map timeouts to **LLM Unavailable**. Other opportunistic rejudge entry points (`rejudge_pending_assessments` after Crawl / file change) stay at **one** Pending per call so Crawl latency is not stacked with a five-call batch. The catalog shows queue progress (`processed_this_load` = budget used this load, `pending_remaining`) — not a spend meter. Match Assessment detail does not advance the queue.

There is **no offline fallback** beyond existing failure rules: LLM Unavailable → required judgments stay **Pending** or keep the prior complete assessment ([0014-assessment-freshness-and-change-detection.md](0014-assessment-freshness-and-change-detection.md)); tailor mid-run failure leaves any prior Preparation Packet untouched ([0013-prepare-flow.md](0013-prepare-flow.md)). No local model, no heuristic scorer, and **Fake is never wired into the normal app path** (Fake stays for tests). Missing key means unavailable, not scripted bands. No budget meter, spend cap, batch-confirm, disk-stored API keys, or key UI — credentials remain env-only; document that assess/Prepare call the live API. The catalog (and Prepare when relevant) shows a short non-secret **LLM Unavailable** reason; never show the key.

**Considered Options:** Multi-provider UI / native Anthropic or Google SDKs; API key or model picker in settings; keys config file on disk; Fake-when-unset so the UI always “works”; local/Ollama offline path; spend caps or confirm-before-batch-rejudge; background / unattended rejudge; until-empty per load; dedicated “Assess more” control; raising Crawl-path rejudge to five. Rejected multi-provider, settings UI, and disk-stored keys for a single-user local tool (env-only); rejected Fake-when-unset because scripted assessments look live; rejected offline scorers so bands stay rubric-honest; rejected cost UI / confirm-before-batch as friction without changing Pending behavior; rejected background rejudge and until-empty to keep spend user-triggered and bounded; rejected Crawl-path budget of five so Playwright Crawl is not stacked with a long judge batch. Fixed catalog budget of five chosen over one to cut refresh churn while staying predictable.
