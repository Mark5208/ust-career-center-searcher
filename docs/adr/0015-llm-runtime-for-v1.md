# LLM runtime for v1

Live Hard Constraint / Preference / Relevance judging and Prepare (Gap Report / Tailored CV / Edit Summary) use one **OpenAI-compatible** HTTP client. Credentials and model come from the environment only: `JOB_FINDING_ASSISTANT_LLM_API_KEY` (required for live calls), optional `JOB_FINDING_ASSISTANT_LLM_BASE_URL` (default OpenAI), and `JOB_FINDING_ASSISTANT_LLM_MODEL` (one model for both `LlmJudge` and `LlmCvTailor`; default when unset e.g. `gpt-4.1-mini`). No key or model UI, no disk-stored secrets, no multi-provider SDK surface in v1.

OpenAI-compatible hosts (e.g. DeepSeek) need their own model id — do not leave the OpenAI default when pointing elsewhere. Example: `JOB_FINDING_ASSISTANT_LLM_BASE_URL=https://api.deepseek.com` and `JOB_FINDING_ASSISTANT_LLM_MODEL=deepseek-chat` (or the host’s current chat model).

**LLM Run (Assessment Summary activity):** Catalog load (`GET /` / `load_assessment_summary_catalog`) is **fast** — it does **not** run a Pending judge batch. The user **explicitly starts** a catalog assess **LLM Run** (or starts **Bulk Prepare**, which is also an LLM Run). At most **one** LLM Run is in flight at a time; a second start is refused or waits with a clear “already judging/preparing…” message. Implementation: process-local run with a thin **status poll** (phase `Judging` / `Preparing`, Job Posting identity, live `k of n` for this run — `n = k + remaining Pending including current`, so `n` can grow if Crawl adds Pending) and a **Stop** flag; Assessment Summary only — not Match Assessment detail, not Master CV Enrichment progressive UI in this decision. Catalog assess drains **until Pending is empty** (sequential; each saved/skipped/non-unavailable failure advances the queue; no per-start attempt cap; no start confirm). Bulk Prepare stays uncapped per ADR-0013. On **LLM Unavailable** for an attempt, stop the rest of that run early. A judge failure or skip must **not** starve later Pending ids: the process defers the failed head and advances the queue, then retries deferred heads after a full pass. **Stop**, leave/refresh, or a Master CV / Hard Constraints / Preferences **fingerprint change** mid-run: cooperative abort — finish the **current** posting’s provider call and apply normal success/failure rules; do **not** start the next; keep successes already saved; no auto-resume of the interrupted run (file-change abort does not auto-start a new drain). HTTP calls use a short timeout and map timeouts to **LLM Unavailable**. Opportunistic rejudge after Crawl / file change (`rejudge_pending_assessments`) stays at **one** Pending per call with **no** LLM Run banner — do not stack Playwright Crawl with a long assess run. No spend meter, ETA, or cost UI.

There is **no offline fallback** beyond existing failure rules: LLM Unavailable → required judgments stay **Pending** or keep the prior complete assessment ([0014-assessment-freshness-and-change-detection.md](0014-assessment-freshness-and-change-detection.md)); tailor mid-run failure leaves any prior Preparation Packet untouched ([0013-prepare-flow.md](0013-prepare-flow.md)). No local model, no heuristic scorer, and **Fake is never wired into the normal app path** (Fake stays for tests). Missing key means unavailable, not scripted bands. No budget meter, spend cap, batch-confirm, disk-stored API keys, or key UI — credentials remain env-only; document that assess/Prepare call the live API. The catalog (and Prepare when relevant) shows a short non-secret **LLM Unavailable** reason; never show the key.

### Parallel catalog assess (revisited 2026-08-12)

Catalog assess (**Judging**) may run several judge calls concurrently; **Bulk Prepare stays sequential and fully unaffected** (including its `k`/status-display mechanics — see below). Concurrency comes from a new env-only knob, `JOB_FINDING_ASSISTANT_CATALOG_ASSESS_MAX_CONCURRENCY`: default **3** when unset; clamped to **1–10**; unset, invalid, or non-numeric values silently fall back to 3 (no error surfaced). Setting it to **1** yields the same success/failure/early-stop/deferral outcomes as today's sequential engine (the live status shape differs — see `k` below — because that shape change is scoped to catalog assess regardless of the configured concurrency).

Mechanism: one shared thread-safe Pending queue backs idle claimants, who atomically pop the next non-skipped id; the queue tops up from `CatalogStore` so a Job Posting added by Crawl mid-run still joins the same drain (`n` can still grow). HOL-avoidance generalizes today's single-cursor `_rejudge_skip_ids` to a shared skip set: a failed or skipped head is deferred so other claimants are not starved, and the skip set clears once the shared queue has fully drained, allowing one retry pass. `LlmRunStatus` reports the **list** of in-flight Job Posting identities (up to the configured concurrency) while Judging; for catalog assess only, `k` counts postings **fully finished** (saved, skipped, or failed) and never an in-flight one, while `n` keeps today's rolling-total meaning (`n = k + remaining Pending`, including any currently in-flight). **Bulk Prepare's status fields and `k`/`current_index` counting are unchanged** — Preparing still reports one identity and still counts the in-flight posting toward its `current_index`, exactly as today.

**Stop** generalizes to every in-flight call: cooperative, no hard-cancel — every currently in-flight provider call is allowed to finish and apply its normal success/failure rules; no new claim starts; because calls run in parallel, worst-case wait for Stop (or for early-stop below) stays bounded by the single 30s HTTP timeout, not multiplied by the number of in-flight calls. **LLM Unavailable and rate limits are unchanged**: any provider HTTP error, including 429, still maps to LLM Unavailable via the existing client (`llm_runtime.py`); on the first such error from any in-flight call, the run still **early-stops** — other in-flight calls finish cooperatively (same as Stop), then the run ends. No new backoff, retry, or adaptive rate-limit machinery is added; the concurrency env var is the user's own manual dial. **SQLite writes stay safe** without WAL: `CatalogStore.save_match_assessment` calls are serialized behind one new dedicated app-level lock (distinct from `_llm_run_lock`, which continues to guard only run-state bookkeeping); reads are unaffected, and a save is milliseconds against seconds of judge latency, so the lock adds negligible contention.

**Considered Options:** Multi-provider UI / native Anthropic or Google SDKs; API key or model picker in settings; keys config file on disk; Fake-when-unset so the UI always “works”; local/Ollama offline path; spend caps or confirm-before-batch-rejudge; spend/activity meter as the primary ops UX; background / unattended rejudge; keeping a fixed catalog assess budget of five (start again to continue); keeping Pending judge batch on `GET /`; raising Crawl-path rejudge to five; parallel judging in this ship; hard-cancel of the in-flight provider HTTP call; progressive LLM Run UI on Match Assessment single Prepare / Enrichment; continuing an assess LLM Run across a candidate-file fingerprint reset. Rejected multi-provider, settings UI, and disk-stored keys for a single-user local tool (env-only); rejected Fake-when-unset because scripted assessments look live; rejected offline scorers so bands stay rubric-honest; rejected cost/spend UI (provider billing site is enough); rejected background unattended rejudge to keep spend user-triggered; rejected judge-on-`GET /` because multi-minute sequential calls freeze the catalog — explicit start + live status instead; rejected Crawl-path budget of five so Playwright Crawl is not stacked with a long judge batch; rejected parallel judging for this ship (park for later); rejected hard provider abort in favor of cooperative Stop; deferred Prepare/Enrichment progressive UI as thin reuse later; rejected continuing across fingerprint reset so a catalog-wide Pending wave is a new user decision. **Until-empty catalog assess** (revisited): earlier rejected to keep spend bounded by “start again”; accepted once LLM Run activity UX shipped — Stop / leave / Unavailable / file-change abort bound spend better than repeated Assess Pending clicks. **Parallel catalog assess** (revisited): earlier rejected for this ship (see above); accepted now for catalog assess only via a new env var and a shared-queue thread pool (parent issue #25). Rejected alongside it: parallelizing the three per-posting signal calls (Hard Constraint / Preference / Relevance) instead of across postings; static partitioning of the Pending list instead of a shared claim queue; WAL journal mode (a plain app-level lock is simpler and sufficient at this volume); adaptive/backoff rate-limit handling (the concurrency knob is the user’s own manual dial); a new `CONTEXT.md` term or a new ADR number (this is this ADR’s own third revision); redefining Bulk Prepare’s `k`/status-display to match (kept unaffected instead); and a generic `_LLM_MAX_CONCURRENCY` env var name (renamed to `_CATALOG_ASSESS_MAX_CONCURRENCY` to match its actual, narrower scope).
